## 1. 技术选型（用什么做）

| 层 | 选型 | 选型理由 |
|----|------|---------|
| 前端 | Vue3 + Element Plus + Vite | 对应《Web 前端开发》课程；组件化表单交互成熟，Day1 静态版已验证交互模型 |
| 后端 | Spring Boot 3 + Spring Data JPA | 对应《Java 程序设计》课程；分层结构（Controller/Service/Repository）便于讲述 AI 协作下的职责边界 |
| 数据库 | H2（文件模式） | 零安装、落盘重启不丢、支持唯一索引与约束——教学演示场景够用，二期可平移 MySQL |
| HTTP 客户端 | axios（统一拦截器） | 响应统一解包 `Result.data`，错误只透传后端 message |
| 构建 | Maven（阿里云镜像）/ npm | 本机为用户级 zip 安装，路径见 AGENTS.md §3 环境陷阱 |

## 2. 架构与模块划分（模块怎么分）

```
浏览器 :5173                后端 :8080                    H2 文件库
┌─────────────────┐   /api  ┌──────────────────────┐     ┌──────────────┐
│ frontend (Vue3)  │ ──────▶ │ backend (SpringBoot) │ ──▶ │ data/        │
│                  │  代理    │                      │     │ reservation  │
│ views/           │         │ controller/ 接口层    │     │ .mv.db       │
│  ReservationView │         │ service/    业务规则  │     └──────────────┘
│ components/      │         │ repository/ 数据访问  │
│  DeviceCard      │         │ entity/     表映射    │
│  ReservationDialog│        │ dto/        传输对象  │
│ api/reservation.js│        │ exception/  异常→Result│
└─────────────────┘         │ config/     CORS 等    │
  身份：localStorage         └──────────────────────┘
  key=reservation-user        时间边界唯一裁判：服务器时间
```

**分层职责**（AI 改动必须落在正确的层）：
- `controller/`：只做参数接收与 Result 包装，不写业务判断
- `service/`：业务规则（冲突校验、14 天窗口、归属校验）都在这里
- `repository/`：只写查询，`existsBy...` / `findBy...` 命名查询优先
- `dto/`：对外契约（含校验注解），entity 不出 service 层

## 3. 数据模型（数据怎么存）

```sql
-- 器材字典
CREATE TABLE device (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  name         VARCHAR(100) NOT NULL,          -- 器材名
  description  VARCHAR(255)                    -- 用途说明
);

-- 预约记录（核心表）
CREATE TABLE reservation (
  id               BIGINT AUTO_INCREMENT PRIMARY KEY,
  device_id        BIGINT      NOT NULL,
  reservation_date DATE        NOT NULL,       -- 预约日期
  period           VARCHAR(10) NOT NULL,       -- 时段：'上午' | '下午'
  user_name        VARCHAR(50) NOT NULL,       -- 借用人（姓名即身份）
  created_at       TIMESTAMP   NOT NULL,       -- 提交时间（排序用）
  CONSTRAINT uk_reservation_slot
    UNIQUE (device_id, reservation_date, period)  -- ★ 冲突防护的数据库底线
);
```

**关键设计：唯一索引 `uk_reservation_slot`**
"同一器材同一日期同一时段只能被约走一次"这一业务铁律，最终由数据库约束保证——即使 Service 校验被并发绕过，`saveAndFlush` 也会抛 `DataIntegrityViolationException`，被转成 409。

## 4. 冲突防护三层（并发类需求必须沿用）

```
请求 ──▶ ① Service 前置查询 existsByDeviceIdAndDateAndPeriod
            │ 命中 → BizException(409, "{器材}在 {日期} {时段} 已被预约，请更换时段")
            ▼ 未命中
         ② saveAndFlush 写入
            │ 并发撞唯一索引 → DataIntegrityViolationException
            ▼
         ③ GlobalExceptionHandler 统一捕获 → Result(409, 同文案)
            ▼
         前端拦截器只弹后端 message，弹窗内 el-alert 持久展示
```

## 5. 接口契约（现状 + 演进）

Base：`/api`，响应统一 `Result{code, message, data}`（`/api/ping` 例外）。完整契约表见 AGENTS.md §5，摘要：

| 接口 | 状态 | 说明 |
|------|------|------|
| GET `/api/ping` | ✅ | 健康检查，裸 JSON |
| GET `/api/devices` | ✅ | 器材列表 |
| POST `/api/reservations` | 🔶 | 提交预约；演进中：+14 天窗口、status 字段、user ≤50 校验 |
| GET `/api/reservations?user=` | 🔶 | 我的历史；演进中：LIMIT 200、缺参 400 封装 |
| GET `/api/reservations/stats?user=` | ✅ | 成功次数（口径：累计成功预约数，含已结束） |
| DELETE `/api/reservations/{id}?user=` | 🆕 | 取消预约（仅本人，403 拦他人） |

## 6. 关键技术决策记录（ADR 摘要）

| 决策 | 结论 | 备选与否决理由 |
|------|------|---------------|
| 冲突判定放哪层 | 数据库唯一索引兜底 + Service 前置校验 | 只放应用层：并发双击会穿透；只放数据库：无法给出友好文案 |
| 状态由谁计算 | 后端服务器时间下发 `status` | 前端本地时间：跨时区/改系统时间时当天边界出错 |
| 器材初始化 | `data.sql` 现状 → P1 改 ApplicationRunner 空表才插 | 保留 DELETE 重插：二期器材管理的新增数据会被清掉 |
| 前后端部署形态 | dev 分离（vite 代理）/ prod 同源（Boot 托管静态资源） | 一直分离部署：教学演示需起两个服务，且 CORS 全放行有安全债 |

## 8. 部署与运行

**开发（现状）**：`run-backend.cmd`（:8080）+ `run-frontend.cmd`（:5173，/api 代理），H2 console 开放便于查库。

**演示（Day8 起，见看板 T8）**：`prod` profile 关 H2 console；前端 `vite build` 产物由 Spring Boot 同源托管，删除 CORS 全放行——单端口 `:8080` 直接演示，换机器只需 JDK + 一条命令。

## 9. 测试与验收策略

无自动化测试框架（教学范围外），以**双通道验收**替代并写入每个任务：
1. **浏览器实测**：完整用户路径（含错误路径，如连点两次预约看 409）
2. **curl 复测**：每个接口验证成功路径 + 全部错误码（400/404/403/409）

数据库正确性演示手法：H2 console 直查表，展示唯一索引结构与记录。
