## 反思区（今天指挥 AI 干成了什么 / 坑在哪）

实验二的主线是"需求三件套 + 规则文件 + Git 分支"。按手册"分步喂"的策略，我把 Day1 电梯稿和已跑通的全栈现状喂给 AI，一次只要一个文档：先 PRD（只谈做什么、给谁、怎么算成功，禁止写代码）→ 再技术方案（选型理由、数据模型、冲突三层、ADR）→ 再任务看板（把 AGENTS.md 已拍板的 T1–T8 切成 Day3–Day8 排期，每条 ≤1 天）。最大收获是理解了"三件套逻辑"：AI 不是不听话，是你没给它听话的格式——PRD 的"验收口径"列写得多具体，后面任务就拆得多顺。

坑一个：写看板时差点把"响应纪律"当成普通注释随手加，回头看要求才发现 C1 是独立挑战项，须观察后续会话行为差异——于是把它做成 AGENTS.md 的 §0（每个会话最先读到、优先级最高），共 7 条，最关键的是"不确定就先问，不要猜表结构"和"红线即终审"（防止我自己口头反悔破坏范围纪律）。

## 三件套的取舍逻辑（审题时能讲清楚）

- **PRD 一页纸**：范围 = 电梯稿三个功能不动摇 + P0 增强项（取消/14 天/状态后端下发）；成功标准全部可演示、可量化，第 5 条直接挂收工四步——文档不是摆设，是每天的验收依据。
- **技术方案**：核心是三条"唯一"：冲突底线唯一（数据库唯一索引）、时间裁判唯一（服务器时间）、API 出口唯一（前端只走 reservation.js）。ADR 表记下了四个关键决策及否决理由，比"我们用了 XX 技术"有说服力。
- **任务看板**：每条任务 = 一次 AI 对话能干完的块 + 双通道验收口径；Day6 留给跨仓库 PR（对应手册第 6 天的队友仓库协作）。

## C1 观察计划（响应纪律的效果验证）

后续每次会话按 §0 七条逐条观察，重点记录：① AI 是否在改代码前先给计划；② 拿不准时是否提问而不是猜；③ 我口头提到"要不加个登录"时，AI 是否引用红线 Q2 先确认例外。观察结果记入 day3+ 反思件。

## 对话档案

### 档案一：三件套（T1）

- **我的指令**：把电梯稿喂给你，按实验二要求分步产出三件套——先只写 PRD 不要写代码；审改后再要技术方案；再要任务拆解（每条 ≤1 天）。产出 docs/PRD.md、docs/技术方案.md、任务看板。
- **AI 的关键动作**：PRD 把"怎么算成功"落成 5 条可量化验收（含 409 演示瞬间、数据可靠、边界一致）；技术方案补了 ADR 决策记录（冲突判定放哪层/状态谁算/初始化策略/部署形态，各附否决理由）；看板把 AGENTS.md §6 的 T1–T8 映射到 Day3–Day8，每条带四步验收口径。
- **结果**：组内互审通过（3 分钟能看懂做什么、怎么验收），文档三向互链。

### 档案二：响应纪律（C1）

- **我的指令**：给 AGENTS.md 加"响应纪律"条款（如"不确定就先问，不要猜表结构"），要能观察后续会话的行为差异。
- **AI 的关键动作**：新增 §0 七条款置于全文最前：先说计划/不确定先问/只做被要求的事/破坏性操作先确认/附 diff 说明/红线即终审/文案只出自后端；并在文件头部补了三件套文档导航。
- **结果**：条款全部可观察可检验，day3 起逐条记录行为差异。

### 档案三：分支演练（T3 前置）

- **我的指令**：按手册"单人也练分支"：开 feat/docs-day2 分支提交三件套与规则文件改动，测试无冲突后合回 master，保留合并轨迹。
- **AI 的关键动作**：`git checkout -b feat/docs-day2` → 提交 → `git checkout master` → `git merge --no-ff`（保留分支拓扑）→ 推送。
- **结果**：见本次 merge commit；跨仓库 PR（fork 组长仓库改欢迎语）在 Gitee 网页手动完成。
