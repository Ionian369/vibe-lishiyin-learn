一页想法电梯稿

教务器材预约 · 五分钟讲清楚一个想法

壹

给谁 · 解决什么问题

  1. 给借器材的人——普通同学、社团干事：借投影仪、音响、无线话筒靠班群接龙，谁先约到全凭记忆，到了现场才发现设备被人拿走。
  2. 给管器材的人——课代表、教务器材管理员：每周手工核对共享表格，两个班约了同一台投影仪只能现场扯皮。
  3. 系统做什么——把「同一器材 + 同一日期 + 同一时段」做成只能被约走一次：第二次提交当场被拒（409），红字提示到具体器材与时段。
贰

核心功能 · 恰好三个

功能一

浏览器材

首屏三张卡片——投影仪 / 音响 / 无线话筒，含名称与用途说明，空闲与否一眼可辨。

功能二

提交预约

选日期与上午／下午时段提交；同一器材同一时段第二次提交返回 409，弹窗持久展示冲突原因，改选即可重试。

功能三

查询历史

填姓名即出「我的预约历史」：器材 / 日期 / 时段 / 待使用或已结束 / 提交时间，成功次数实时累计。

叁

凭什么做得完

  • Web 前端开发 Vue3 + Element Plus 组件化与表单交互；Day1 上午已一句话生成静态版并实测通过。
  • Java 程序设计 SpringBoot + JPA 分层结构（Controller / Service / Repository），骨架当天已跑通。
  • 数据库原理 H2 + UNIQUE(device_id, date, period) 唯一索引，并发抢同一时段由索引兜底——不只是应用层判重。
肆

最大风险一条 · 对策各一

最大风险

无登录体系，姓名即身份。任何人填别人的姓名，就能以他人名义占用时段、查看他人历史。

唯一对策

明示边界 + 留好接口。Day1 场景限定班内互信，演示时说明这是已知边界；数据表预留 user_name 字段，二期接学号登录，不改表。

伍

审题三问

问一用户真实存在吗？

存在。我自己借投影仪就遇过「接龙排到我但设备被拿走」；课代表每周核对预约要花一节课。两类用户本班本学期就有，不用想象。

问二砍掉一个功能，行不行？

行。砍掉「查询历史」，主线「约器材 + 冲突拒绝」依然完整成立——历史只是让借的人少问一句「我约上没有」，它是增强项而非生死项。

问三演示第一眼看什么？

连点两次「预约」：第一次绿色成功，第二次红色 409、冲突原因具体到器材／日期／时段——冲突拒绝是本系统的灵魂，是区分「预约系统」和「表单收集器」的瞬间。
